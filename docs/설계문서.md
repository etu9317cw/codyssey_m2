# 설계 문서 — 센터 운영 비서 (M-2)

작성일 2026-10-07 · 과제 목표(스스로 설명할 것) 6개에 답하는 형식으로 썼다.

## 1. 분석 → 요약 → 서비스 흐름 (M-1과의 연결)

```
M-1  data/sample/electricity_daily.csv ──run.py──▶ output/summary.json  (period·count·metrics·recent_7_days·trend)
                     │
                     └── scripts/seed_from_m1.py ──▶ Firestore(data 컬렉션)  {date, value, memo}
                                                           │
M-2  GET /api/data/summary ◀── data_service.compute_summary(전체 레코드)   ← 같은 규칙(최근 7일 vs 직전 7일 ±5%)
                     │
     POST /api/chat ── summary_to_text() → 시스템 프롬프트 → LLM → conversations 저장
```

M-1 리포트의 핵심 수치(기간·개수·평균·최대·최소·최근 7일·추세)와 M-2 요약 필드가 **같은 이름·같은 규칙**이다. M-1에서 "최근 7일이 추석 때문에 −19%"라고 쓴 것이 M-2 비서의 답(S-01)에 그대로 나타난다.

## 2. 계층 분리 기준

| 계층 | 폴더 | 책임 | 하지 않는 것 |
|---|---|---|---|
| Router | `app/routers/` | 경로·HTTP 메서드·상태 코드·응답 모델. 요청을 받아 서비스에 넘기고 결과를 돌려준다 | 계산, DB 접근, LLM 호출 |
| Service | `app/services/` | 비즈니스 규칙: 요약 계산, 제목 생성, 컨텍스트 주입, 저장 시점 결정, LLM 재시도 | HTTP 상태 코드 결정(예외만 던짐), 저장 방식 |
| Repository | `app/repositories/` | 문서 저장·조회. `Repository` 인터페이스 하나에 `MemoryRepository`·`FirestoreRepository` 두 구현 | 비즈니스 규칙 |
| Core | `app/core/` | 환경변수, 예외→JSON 변환, Firebase 초기화 | 도메인 지식 |

**왜 이렇게 나눴나**: ① 테스트 — 서비스는 memory 저장소 + LLM mock으로 외부 없이 검증(17개). ② 교체 — Firebase 키가 없는 채점 환경에서도 `STORAGE=memory`로 전체가 돈다. ③ 설명 — "라우터는 문, 서비스는 머리, 저장소는 창고"로 말할 수 있다.

## 3. API 표

| 메서드·경로 | 요청 | 응답 | 오류 |
|---|---|---|---|
| `GET /api/health` | — | `{status, storage, llm_configured, model, label, unit}` | — |
| `GET /api/data/summary` | — | `Summary` (아래) | — |
| `GET /api/data?limit&order` | query | `DataOut[]` 날짜순 | 400 |
| `POST /api/data` | `{date, value, memo}` | 201 `DataOut` | 400 검증 |
| `GET /api/data/{id}` | — | `DataOut` | 404 |
| `PUT /api/data/{id}` | 일부 필드 | `DataOut` | 400, 404 |
| `DELETE /api/data/{id}` | — | 204 | 404 |
| `GET /api/conversations?limit` | — | `[{id, title, message_count, created_at, updated_at, preview}]` | — |
| `POST /api/conversations` | `{title?, messages?}` | 201 대화(메시지 포함) | 400 |
| `GET /api/conversations/{id}` | — | 대화 + `messages[]` | 404 |
| `DELETE /api/conversations/{id}` | — | 204 | 404 |
| `POST /api/chat` | `{message, conversation_id?}` | `{conversation_id, answer, summary_used, model}` | 400 빈 메시지, 404 없는 대화, 502 상위 오류, 503 LLM 미설정 |

`Summary` = `{label, unit, period{start,end}, count, metrics{total,average,max,min}, recent_7_days{total,average,count}, trend, trend_change_pct, top_memo, latest{date,value,memo}}`

라우트 순서: `/api/data/summary`를 `/api/data/{id}`보다 **먼저** 등록한다. 반대로 하면 `summary`가 id로 해석되어 404가 난다(테스트 `test_summary_route_not_shadowed_by_id`).

대화 불러오기 방식: 미션 선택지 중 **(A)** `GET /api/conversations/{id}`. 목록은 가볍게(요약만), 상세는 따로. 문서 1개 = 대화 1건이며 `messages` 배열에 턴이 누적된다.

## 4. Pydantic 검증을 쓰는 이유

| 필드 | 규칙 | 안 막으면 생기는 일 |
|---|---|---|
| `date` | `YYYY-MM-DD`, 실제 존재하는 날짜 | `2026-13-01` 같은 값이 저장돼 정렬·요약이 깨짐 |
| `value` | 숫자, 0 이상 | 문자열·음수가 평균 계산에 섞임 |
| `memo` | 200자 이하 | 프롬프트가 길어져 토큰 낭비·400 |
| `message` | 공백 제거 후 1~1,000자 | 빈 호출로 LLM 과금, 긴 입력으로 프록시 400 |

검증 실패는 FastAPI 기본 422 대신 **400 + `{error, message, details}`**로 통일했다(`core/exceptions.py`). 프론트는 `message`만 보여 주면 된다.

## 5. Firestore CRUD와 저장소 추상화

- 컬렉션 `data`: 문서 = `{date, value, memo, created_at, updated_at}`. 정렬은 `date` 문자열(ISO라 사전순 = 시간순).
- 컬렉션 `conversations`: 문서 = `{title, messages[], created_at, updated_at}`. 목록은 `updated_at` 내림차순.
- `Repository` 인터페이스: `list / get / create / update / delete / count`. Firestore 구현은 `firebase-admin`의 `collection().document()`를, memory 구현은 dict + JSON 파일을 쓴다.
- Firebase 초기화는 **지연**(첫 요청 때)한다. 키가 없으면 앱이 죽지 않고 memory로 시작한다.
- 서비스 계정 키는 JSON 파일 경로/문자열 **또는** `PROJECT_ID / CLIENT_EMAIL / PRIVATE_KEY` 3개 변수로 받는다. Render 환경변수에는 후자가 편하다.

## 6. 컨텍스트 주입 원리

1. `/api/chat`이 들어오면 **매번** `compute_summary()`로 최신 요약을 만든다(캐시 없음 → 데이터를 고치면 바로 반영).
2. `summary_to_text()`가 요약을 6~7줄 문장으로 바꾼다. 숫자는 요약에 있는 것만 들어간다.
3. 시스템 프롬프트 = 역할·규칙 5개 + 요약 문장. 규칙 핵심: "요약에 없는 수치는 만들지 말고 없다고 말하라".
4. 이전 대화는 최근 6턴만 넘긴다(토큰 절약, 프록시 400 예방).
5. LLM 응답이 **성공한 뒤에만** user·assistant 메시지를 저장한다. 실패하면 빈 대화가 남지 않는다(테스트 `test_chat_without_llm_key_returns_503`).
6. 프록시가 400을 돌려주면 규칙을 한 줄로 줄인 짧은 시스템 프롬프트로 1회 재시도한다(A-2·A-3에서 확인한 프록시 특성).

왜 Function Calling이 아니라 주입인가: 미션 필수 요구가 주입 방식이고, 요약 7줄이면 토큰이 적어 매 호출에 넣어도 부담이 없다. 개별 레코드 질문("최대 사용일은 언제")에는 답하지 못하는 한계가 있고, 이는 보너스(도구 호출)의 동기가 된다.

## 7. 배포 환경의 CORS·환경변수·키 관리

| 항목 | 설계 |
|---|---|
| CORS | `ALLOWED_ORIGINS`(쉼표 구분) + `https://*.vercel.app` 정규식. 메서드는 GET/POST/PUT/DELETE/OPTIONS만 |
| 키 위치 | 서버 환경변수만. 프론트는 `API_BASE_URL`만 알고 LLM·Firebase 키는 절대 받지 않는다 |
| 이름 호환 | `OPENAI_API_KEY`/`CODYSSEY_API_KEY`, `OPENAI_BASE_URL`/`CODYSSEY_BASE_URL` 둘 다 인식 → 채점자가 개인 키로도 실행 가능 |
| 콜드스타트 | Render 무료 티어 첫 요청 최대 50초 → 프론트 health 60초, 채팅 50초 타임아웃, 배지로 상태 표시 |
| 로컬 vs 배포 | 로컬 `.env` + memory, 배포 환경변수 + firestore. 코드는 같다 |

## 8. 오류 처리 표

| 상황 | 백엔드 | 프론트 표시 |
|---|---|---|
| 빈 입력·형식 오류 | 400 `validation_error` | 폼 아래 빨간 메시지 / 채팅 "질문을 입력하세요" |
| 없는 id | 404 `not_found` | 메시지 표시, 채팅은 대화를 새로 시작 |
| LLM 키 없음 | 503 `llm_not_configured` | "서버에 LLM API 키가 설정되지 않았습니다" |
| 프록시 401/403 | 502 `upstream_error` "키가 거부" | 오류 말풍선 |
| 프록시 400 | 짧은 프롬프트 재시도 → 실패 시 502 | 오류 말풍선 |
| 타임아웃(20초) | 502 "응답 시간 초과" | 오류 말풍선 |
| 네트워크 끊김 | — | "서버에 연결할 수 없습니다" + 상단 배지 빨강 |
| 프론트 타임아웃(채팅 50초) | — | "응답이 지연되고 있습니다" |

## 9. 과금·안전 장치

- 입력 1,000자, 메모 200자, 이전 대화 6턴, 재시도 1회, 버튼 비활성화(중복 전송 방지).
- `max_tokens` 생략 이유: gemini-3-flash는 사고 토큰이 상한에 포함되어 작게 주면 본문이 빈다(A-2에서 확인). 대신 입력 쪽을 제한한다.
- 서버 로그에 메시지 본문을 남기지 않는다. 대화는 기능상 저장되므로 개인정보 입력 금지 문구를 화면에 둔다.
